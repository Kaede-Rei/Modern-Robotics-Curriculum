# 机器人软件架构：从算法模块到可靠任务

> **问题：** 每个单独的视觉、导航、机械臂节点都能运行，为什么整套机器人仍会“导航完卡住，机械臂不动作”

**先修：** E02、C09、C10；**学习目标：**区分算法、任务编排与执行监督，理解 MoveIt2、Nav2、FSM/BT 之间的职责，以及失败恢复设计

## 核心｜1. 从数据流到任务流

一个机器人系统至少需要三个不同层级

1. **感知与状态层**：报告目标、机器人位姿、健康状态与不确定度
2. **规划与控制层**：生成可执行的路径、轨迹和驱动指令
3. **任务层**：决定何时开始、取消、重试、退避及完成

错误的设计是让视觉节点在检测到目标时直接给驱动器发送不受约束的动作，绕过任务监督、碰撞检查与安全许可

## 核心｜2. MoveIt2 与 Nav2 解决的问题不同

MoveIt2 重点处理机械臂的运动规划，例如机器人模型、规划场景、碰撞检查、路径规划与轨迹时间参数化；**规划成功**表示在模型与规划时刻的场景假设下找到符合指定约束的解，不代表执行过程没有目标移动、定位漂移或突然出现的障碍

Nav2 重点处理移动机器人定位、路径与控制、代价地图、行为恢复与导航任务接口；底盘到达目标位姿不意味着机械臂已就位，也不意味着相机能看到目标

典型移动操作任务需要两个系统之间共享坐标、时间和执行互锁，例如 **导航到观测位 → 停车确认 → 感知目标 → 更新规划场景 → 规划机械臂 → 执行 → 验证结果**

## 核心｜3. 有限状态机 FSM 与行为树 BT

FSM 显式定义状态及转移条件，适合任务阶段边界明确、需要可审计状态的系统；BT 通过 Sequence、Fallback 等控制节点组合动作，适合重试、条件检测与任务层复用

二者不冲突：可以由一层状态机处理系统模式（待机、自动、人工、故障等），在自动任务内部使用行为树；**任务树返回 SUCCESS 不应覆盖底层故障锁存或安全停机状态**

一条合理的任务控制链是

```text
operator request
   -> system readiness / safety gate
   -> navigator Action
   -> stop and localization check
   -> perception quality gate
   -> MoveIt2 planning & execution
   -> target outcome verification
   -> success / recovery / abort
```

## 进阶｜4. 将每个动作定义成契约

任务节点至少应规定前置条件、超时、成功观测条件、失败原因、取消语义和资源占用；例：机械臂“到达目标位姿”的成功不应只来自规划器成功，而应综合实际关节位置或末端位姿反馈及允许误差

以下是不严谨的 API 语义：`pick() -> True`；更明确的结果至少要区分“命令已接受”“执行已结束”“任务目标已验证”；如果缺少力/视觉反馈，不能声称已经稳定抓取

## 进阶｜5. 并发、资源互斥与恢复

当两台机械臂共用工作空间时，应管理碰撞区域与资源所有权；不能只依赖分别执行时的各自无碰撞轨迹；并发动作需描述取消时机、回滚能力和“执行了一半”的物理后果

重试策略应有次数上限、退避条件及失败区分；由于传感器掉线导致的失败不能靠无限重复 IK 或重发电机指令解决

## 实践｜6. 移动操作架构审查练习

画出七个模块：感知、定位/导航、手眼变换、规划场景、机械臂规划/控制、任务监督与安全链；为每条边标注时间戳、消息方向、超时、失败状态以及谁拥有取消权

检查三类反例：导航成功但定位协方差过大；目标视觉检测滞后；机械臂控制器返回已发送但驱动器尚未到位；能解释这三种情形为何不能无条件进入下一动作，说明已经理解任务级集成
