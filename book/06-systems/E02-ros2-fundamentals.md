# ROS2：通信、坐标变换与控制接口

> **问题：** 相机已经发布了目标位姿，机械臂节点也收到了消息，为什么机器人仍可能朝错误位置运动

**先修：** M01、P02、E01；**学习目标：**根据数据语义正确选择 ROS2 通信形式，掌握 TF2 的时空一致性，理解 `ros2_control` 的职责与边界

## 核心｜1. ROS2 不是控制算法

ROS2 提供机器人程序的通信和组织机制，而不是自动保证算法精度、实时性或硬件安全；常见组成包括节点、消息、服务、Action、参数、生命周期、日志和时间系统

| 机制 | 合适的使用场景 | 易混淆点 |
|---|---|---|
| Topic | 连续传感器、状态流和异步事件 | 收到一条消息不代表数据实时有效 |
| Service | 短时请求/响应与配置操作 | 不适合长期占用且必须反馈进度的任务 |
| Action | 可取消、持续执行、有反馈的目标 | Action 成功只说明该服务自己的完成语义 |
| Parameter | 可配置的运行参数 | 参数值合法不代表动力学稳定或安全 |
| Lifecycle | 受控配置、激活与停止 | 节点激活不等于整机已具备运动许可 |

ROS2 通常以 DDS/RMW 实现传输抽象；实际通信兼容性还取决于 QoS 兼容性、网络拓扑、消息大小和所选中间件实现

## 核心｜2. QoS 要按数据语义配置

传感器流和命令流不能统一套用同一个 QoS；常见策略包括可靠性（Reliable / Best effort）、历史深度、持久性和期限等；只改变队列深度不能证明信息不会丢失或过期

一个较高频的传感器流通常可优先评估低等待、允许丢弃旧帧的配置；关键命令则应结合端到端确认、超时机制和执行器端状态回读设计，而非简单声称 `reliable` 就具备可靠控制

**实际使用前应查看具体 ROS2 发行版的官方 QoS 文档和节点接口声明**，不要把教程里的配置示意直接粘贴到任意设备上

## 核心｜3. TF2 的空间关系与时间关系

以 $^A T_B$ 表示将 B 坐标表达转换到 A 坐标表达的齐次变换，则

$$
{}^A T_C(t)={}^A T_B(t)\,{}^B T_C(t)
$$

在运行系统中，变换不仅要满足**坐标链连通**，还应在消息时间戳附近存在有效的插值或查询结果；一个常见错误是拿当前最新的 `base_link → camera` 关系转换数百毫秒之前拍摄的运动目标

例如机械臂末端相机的 `camera_optical_frame` 一般有自己的光学轴约定；将其数值直接作为 `base_link` 位置会在方向、符号和偏置上都出错；必须结合 P02 手眼标定和 F05 坐标约定

## 进阶｜4. `ros2_control` 的三层结构

典型设计包括 **hardware_interface → controller_manager → controllers**；硬件层声明命令与状态接口，控制器依据接口类型工作，管理器安排控制器生命周期、资源管理与更新

例如同一执行器可能暴露 `position`、`velocity`、`effort` 中的部分接口；控制器能否切换依赖硬件实现、控制器本身和驱动器能力，**不能把统一的 ROS2 接口名称当成硬件支持证据**

发布位置命令、读取状态并不能替代电机掉线检测、限位保护、驱动上电许可或安全停机机制，见 E05

## 进阶｜5. 组件、Executor 与定时回调

节点回调由 Executor 调度；单线程、多线程及回调组配置会影响响应时间和回调是否相互阻塞；即便使用多线程，阻塞回调和共享资源争用仍可能导致延迟

拆成更多节点不必然降低延迟；进程内组合、消息拷贝、网络负载及日志频率都需要实测；参见 E01 的响应时间和 E07 的分阶段记录

## 实践｜6. 不连接真机的最小接口检查

首先写出一个机器人接口表，至少包括消息类型、坐标系、时间戳来源、频率、QoS、超时阈值及故障状态；再在可运行的 ROS2 环境中用 `ros2 topic info -v`、`ros2 interface show` 和 `ros2 node info` 查看**实际运行中**的接口；使用 TF2 相关工具查询已发布坐标链

这些命令属于读者可进行的工程练习，**配套练习不包含实际 ROS2 节点部署或硬件驱动运行**
