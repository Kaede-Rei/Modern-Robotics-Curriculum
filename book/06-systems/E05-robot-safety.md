# 机器人安全：从风险分析到独立保护

> **问题：** 系统已经在 ROS2 里订阅了“急停”Topic，为什么这仍不足以说明机器人具有可靠的急停功能

**先修：** E01、C01、E03；**学习目标：**区分控制算法的稳定性、软件异常处理与经过风险评估的安全功能；明确紧急停止、保护停止和恢复的不同语义

## 核心｜1. 稳定、可靠和安全不是同一回事

闭环稳定性证明研究指定模型及假设下的状态行为；软件可靠性关注故障发生概率与功能正确性；**功能安全**则关注故障发生时对人员和设备的风险控制；即使 Lyapunov 稳定，也可能稳定地施加危险接触力

工程上应从危险源识别开始，如夹伤、剪切、撞击、失控运动、意外再启动、重力下坠、末端锋利工具、储能和移动平台碰撞；风险评估应明确可预见的人员暴露、严重度与避免可能性；不能凭某个算法名称直接声称达到安全等级

## 核心｜2. 正常停止、保护停止与紧急停止

**正常停止**由任务逻辑请求结束动作；**保护停止**可能由防护条件、工作区入侵或其他保护措施触发；**紧急停止**面向突发危险的停止需求；它们的触发源、优先级、复位方式及所需硬件架构可能不同

特别注意：急停不等于机械制动“立刻瞬间静止”，也不等于 ROS2 发布零速度；不同应用需要按风险分析确定停车方式、减速曲线、失电和垂直轴保持策略；STO 等驱动安全功能也有各自定义，不能将其与“制动力矩一定存在”混为一谈

## 核心｜3. 故障锁存与恢复许可

一个教学用监督状态机可以采用

```text
INHIBITED -> READY -> ACTIVE
                  |        |
                  +--- fault / stop -> FAULT_LATCHED
emergency stop -----------------------> ESTOP_LATCHED
```

进入故障/急停锁存后，不能因为 Topic 恢复或错误码自动消失就立即重启；恢复过程需要独立验证防护条件、有效的人工复位及再次使能流程；**复位本身不应直接造成危险运动**

此处只是讲解状态逻辑；真正的急停按钮、安全继电器/安全 PLC、安全总线或安全驱动器，需要按对应应用标准和风险评估选择及验证；**在一般进程内实现的 Python 状态机不能作为人员安全功能**

## 核心｜4. 检测失效模式

| 失效 | 可能后果 | 需要核对的保护性质 |
|---|---|---|
| 命令长时间未更新 | 驱动继续执行旧命令 | 独立超时、驱动端安全响应 |
| 编码器失效或跳变 | 闭环反馈不可信 | 传感器诊断、状态一致性检查 |
| 控制进程挂死 | 任务级停止无法执行 | 与主控制软件故障独立的保护机制 |
| 通信中断 | 控制器与执行器失联 | 现场总线或驱动端超时策略 |
| 人员进入工作空间 | 机械碰撞风险 | 风险评估确定的防护与停止机制 |

**机器人级操作模式和系统级安全功能是不同层次**；不能只凭“有保护阈值、有急停按钮”来认定标准符合性

## 进阶｜5. 标准适用范围

- **ISO 10218-1:2025**：工业机器人本体安全要求，适用范围存在明确边界
- **ISO 10218-2:2025**：工业机器人应用和机器人工作站集成相关的安全要求
- **ISO 3691-4:2023**：无人驾驶工业车辆及其系统的安全要求，适用对象不能与所有移动机器人直接等同

这些公开页面可用于确定标准适用对象；**本教材不复制标准的规范性条款，不提供安全合规结论，也不能替代购买或依法获取正式标准文本并进行专业评估**；医疗、无人机、水下与消费级机器人不能简单套用工业机器人标准作为唯一依据

## 实践｜6. 锁存状态教学检查

`labs/python/systems/main.py --check` 运行一个纯软件教学状态机：普通故障后不能无确认自动恢复；急停状态在收到非复位事件时保持锁存；复位必须满足人工确认和保护条件清除；该实验只验证代码定义的状态转移不变式，**不是 SIL/PL/Category 的认证测试**
